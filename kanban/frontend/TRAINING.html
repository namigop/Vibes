The Kanban application

A complete, end-to-end walkthrough: the product, the architecture, the frozen REST contract, the Go backend, the Next.js frontend, the two hard problems (drag-and-drop ordering and optimistic updates), the tests, and the runbook you will need on your first support shift. Read it top to bottom the first time, then use the Contents as a reference.

Part 0Start here

How to read this

You do not need to know Go, Next.js, or SQL to start, but you will find Parts 4–6 much easier if you have seen each language once. Every technical term is defined the first time it appears; the vocabulary you are expected to know on day one is deliberately small.

"Client" / "frontend"

The Next.js app running in the user's browser. It owns no database connection and no secrets.

"Server" / "API" / "backend"

The Go process. The only thing allowed to talk to PostgreSQL. Publicly reachable inside the machine, not to the internet.

"Contract"

docs/API.md — the frozen list of URLs, request bodies, response shapes and error codes. Both halves are written against it; neither owns it.

"Optimistic"

Change the screen immediately, then tell the server. If the server says no, undo. The user never waits for a network round trip.

The one sentence that explains this whole app

Ordering is the only genuinely tricky part. A card or a column has an integer position, the positions in a list are always a gap-free run 0, 1, 2 … n-1, and every move re-numbers both the list the thing left and the list it joined inside a single database transaction. The frontend mirrors that arithmetic locally so the drag feels instant, and throws the local result away if the server disagrees.

The 60-second model

  1. You open http://localhost:3000. The side nav asks the API for the list of boards.
  2. You click a board. The URL becomes /board/<uuid> and the page asks for that board's columns and cards in one request.
  3. You drag a card. The card moves on screen instantly, because the browser is running the same re-ordering algorithm the database will run.
  4. You let go. One HTTP call goes out. If it fails, the screen snaps back and a toast explains why.
  5. Nothing polls. Nothing streams. The screen is a pure function of the last API response plus the edits you have made since.

Part 3The frozen contract

docs/API.md is the agreement between the two halves of the app. Read it end to end once; it is short. It is frozen in the sense that changing a field name means changing both the Go structs and the TypeScript types in the same commit — the document keeps you honest about what you changed.

Error envelope

Every response that is not 2xx has exactly this body. There are no other error shapes.

{
  "error": "validation_failed",        // stable slug — branch on this in code
  "message": "title must not be empty" // human text — safe to show in a toast
}
Statuserror slugMeaningWhat the UI does
400validation_failedBad body, bad UUID, unknown priorityToast the message; keep the form open
404not_foundThat id does not exist (or was deleted)Roll back the optimistic change, then toast
409conflictDuplicate name where uniqueness is requiredToast (defined in the contract; nothing enforces it yet)
500internal_errorUnexpected server faultRoll back, toast a generic message, check the API log

The split between error and message is deliberate: a client can make decisions on the slug without parsing English, and a human can read the message without knowing the slug.

Domain rules

RuleConsequence for you
All ids are UUIDv4 stringsNever derive an id client-side. The database generates it.
priority ∈ low | medium | high | urgent, default mediumA CHECK constraint in Postgres and a set in Go both enforce it; the UI offers a fixed list.
position is a gap-free 0..n-1 ordinal inside its parentNever send a fractional position like 3.5. The server clamps and renumbers; the client mirrors that arithmetic exactly.
due_date is a calendar date "YYYY-MM-DD", or nullNever a timestamp. Never parse it with new Date(str) and reformat. See Part 7.4.
"" and null are equivalent for description/assigneeThe server normalises to "". The client sends a string, never undefined.
Names and titles must be non-empty after trimmingThe client trims before sending and validates before sending, so you get an instant error instead of a round trip.

Move semantics, worked

This is the single most important thing to internalise. Read the algorithm, then read the worked example. 

POST /cards/{id}/move  { "column_id": "…", "position": 2 }

1. position is the index within the destination column AFTER the move.
2. Values outside 0..len are clamped, not rejected.
3. column_id == the card's current column means "reorder in place".
4. Source and destination are reindexed together in ONE transaction, and the
   card is returned with the position the server actually gave it.

Worked example — dragging a card across columns

Starting state (positions shown in brackets):

To Do                 Review
[0] "one"               [0] "alpha"
[1] "two"
[2] "three"

The user drags "one" and drops it on the second slot of Review. The browser sends { column_id: reviewId, position: 1 } — not 2, because after the move "one" is Review's second card.

The server does this inside one transaction:

source ids = [one, two, three]
dest   ids = [alpha]

nextSource = removeID(source, one)            = [two, three]
nextDest   = insertAt(dest, clamp(1, 1), one) = [alpha, one]

write positions:  two→0, three→1  (source reindexed)
                 alpha→0, one→1   (dest reindexed, and one's column_id is set first)

commit  →  returns { …"one", "column_id": review, "position": 1 }

Final state:

To Do                 Review
[0] "two"               [0] "alpha"
[1] "three"             [1] "one"

Notice the source column was renumbered too. That is what makes ordering un-corruptible: there is no way for two cards to end up claiming the same slot, and no fractional positions to accumulate.

Why the server returns the whole column list for a column move

Renumbering five columns means five UPDATEs. Rather than asking the client to guess the resulting order from one number, the server does the arithmetic and hands back the finished list. The frontend therefore replaces its column array with the response instead of patching one entry.

Changing the contract

  1. Edit docs/API.md first. If the document and the code disagree, the code is wrong.
  2. Backend DTOs — backend/internal/api/dto.go. The JSON tags are the contract; the field names are Go-idiomatic behind them.
  3. Backend service — service.go if validation or defaults changed.
  4. Frontend types — frontend/src/lib/types.ts.
  5. Frontend normaliser — frontend/src/lib/api.ts, normaliseCard, if the new field can be null.
  6. Run both checks — make test and cd frontend && npm run build && npm run lint.
  7. Run the parity test — it exercises real request/response shapes and will catch a field you forgot.

Part 4Backend design

Package map

The Go side is four small packages plus one entrypoint. There are exactly two direct dependencies (pgx/v5 and google/uuid) — no web framework, no ORM, no router library. Go 1.22+ ships a pattern-matching HTTP router in the standard library, so mux.HandleFunc("GET /api/v1/boards/{boardId}", …) already does method matching, path wildcards and 405s.

The only asymmetry worth remembering: store duplicates the list of default column names (demoColumns) that also exists in api (DefaultColumnNames). That duplication is deliberate — store cannot import api because api imports store. If you change one, change both.

Boot sequence

Everything happens in main.run(), in this order. Each step is a place startup can fail, and each logs a line you can look for.

  1. Load config — config.Load() reads the environment and applies defaults, so the server starts with zero setup.
  2. Configure logging — slog with a text handler in development (readable) and JSON everywhere else (machine-parseable).
  3. Install a signal handler — signal.NotifyContext for Ctrl-C / SIGTERM. Everything before the server starts uses that context, so a Ctrl-C during a slow migration unwinds cleanly.
  4. Open the pool and ping — store.Open parses DATABASE_URL, builds a pgxpool (max 10 connections) and pings. Failing early beats accepting traffic you cannot serve.
  5. Run migrations — see Part 4.7.
  6. Seed demo data — only if SEED_DEMO is true and the board list is empty.
  7. Build the service and router — one Service holding the query object, one http.Handler chain.
  8. Serve — with explicit timeouts: 15s read, 30s write, 60s idle.
  9. Shut down gracefully — on a signal, srv.Shutdown with a 10s grace period so in-flight requests finish.

Why the timeouts matter

Go's zero-value http.Server has no timeouts, which is a well-known way to exhaust file descriptors. Setting them explicitly is a two-line habit that prevents a whole class of production incident. The shutdown grace period is the mirror image: a user who hits Save during your deploy should still get their save.

Request lifecycle

  • logMiddleware wraps the response writer to capture the status code and byte count, then emits one structured line: method, path, status, bytes, duration. 5xx logs at error level, 4xx at warn, everything else at info.
  • recoverMiddleware converts a panic into {"error":"internal_error", …} with 500. Without it one bad request would kill the process and take the board offline.
  • corsMiddleware answers OPTIONS preflights with 204 and echoes a permitted Origin. Because the app uses no cookies and no Authorization header, it never needs Allow-Credentials.
  • ServeMux matches method + path. A bare GET /api/v1/ catch-all answers 404 with the standard envelope instead of the mux's plain-text message.

The service layer

Handlers are deliberately dumb: read the request, call one service method, write the response. All business rules live in service.go, which is why that file is the only place worth reading to understand the domain.

The four ordering helpers

removeID(ids, id)   → ids without id            (never mutates the input)
insertAt(ids, idx, id) → ids with id spliced in at idx, clamped to [0, len]
clampIndex(pos, n)     → pos clamped to [0, n]    (a stale client can't corrupt order)
withTx(ctx, fn)        → runs fn in a transaction, rolls back on any error

MoveCard composes them. Read it top to bottom — it is about forty lines and it is the heart of the backend: 

tx:
  card := GetCard(id)                     // 404 if missing
  GetColumn(columnID)                     // 404 if the destination is missing
  source := card.ColumnID

  if source == columnID:                   // reorder in place
      ids   := ListCardIDsInColumn(columnID)
      next  := insertAt(removeID(ids, id), clampIndex(position, len(ids)-1), id)
      writePositions(next, …, reassign=false)
  else:                                   // move across columns
      sourceIDs := ListCardIDsInColumn(source)
      destIDs   := ListCardIDsInColumn(columnID)
      writePositions(removeID(sourceIDs, id), …, source, reassign=false)
      writePositions(insertAt(destIDs, clampIndex(position, len(destIDs)), id),
                     …, columnID, reassign=true)   // sets column_id first

  moved := GetCard(id)                    // read back the settled row
commit

Two details a reviewer would ask about: reassign=true sets column_id before writing the destination positions, so the positions it is about to write are consistent with the card's new parent. And the card is re-read at the end so the response reports what the database actually stored rather than what we hoped it stored.

sqlc and the store

The project uses sqlc: you write plain SQL with comments, and it generates typed Go. There is no ORM, no hand-written row scanning, and no runtime reflection.

  • queries.sql annotates each statement: -- name: ListBoards :many. :one means "expect at most one row" and gives you pgx.ErrNoRows for free when there is none.
  • emit_json_tags: true and emit_pointers_for_null_types: true mean nullable columns become pointers, which is how due_date can distinguish NULL from the empty string.
  • The overrides block maps uuid → google/uuid.UUID and timestamptz → time.Time. Without it you get pgx wrappers that serialise as {"Bytes":"…","Valid":true}, which the contract forbids.
  • There is deliberately no date override: sqlc 1.31 does not match one against the pgx/v5 built-in mapping, and keeping pgtype.Date is preferred anyway because its Valid flag is exactly the null-vs-set distinction a nullable calendar date needs.
  • db.go defines DBTX — the three methods the store needs. *pgxpool.Pool satisfies it, and so does a transaction, which is what makes WithTx possible without a second set of generated functions.

Migrations

backend/migrations/ holds numbered .sql files that are embedded into the binary with Go's //go:embed and applied at boot. There is no separate migration CLI.

  1. Create schema_migrations(version text primary key, applied_at timestamptz) if it does not exist.
  2. Read the versions already applied.
  3. Sort the embedded files lexically — that is why they are named 00001_init.sql.
  4. Skip anything already recorded. For the rest: begin a transaction, execute the whole file, insert the bookkeeping row, commit.

Because the DDL and the bookkeeping row share a transaction, a failure leaves the database on the last fully-applied version — never half-migrated. To change the schema you add a new numbered file; you never edit an applied one.

Two copies of the same DDL

migrations/00001_init.sql and sql/schema.sql contain the same schema. The first is what actually runs; the second is what sqlc reads to type your Go. They must stay identical. If you change one, change the other in the same commit, and re-run make generate.

Error mapping

Handlers return plain error values. Three small types carry meaning, and one function turns them into HTTP:

ValidationError{…}  → 400  {"error":"validation_failed"}
NotFoundError{…}    → 404  {"error":"not_found"}
ConflictError{…}    → 409  {"error":"conflict"}
pgx.ErrNoRows       → 404  {"error":"not_found"}
anything else       → 500  {"error":"internal_error"}  + slog.Error with the real cause

The 500 branch never leaks internals to the client — the details go to the server log. That split is deliberate: the message is safe to put in a toast, and the log has what you need to debug.

ER model

Constraints worth knowing

ConstraintWhereWhy it exists
CHECK (length(btrim(name)) > 0)boards, board_columns, cardsWhitespace is not a name. Last line of defence behind the Go validation.
CHECK (priority IN ('low','medium','high','urgent'))cardsThe closed set from the contract, enforced in the database as well as in Go.
NOT NULL DEFAULT ''description, assigneeThere is no "null assignee" concept; empty string is the only meaning.

idx_board_columns(board_id, position)board_columnsEvery board load lists columns in order.
idx_cards(column_id, position)cardsEvery move lists one column's cards in order.

Both indexes are (parent, position) composites — the server's two hottest reads are "children of X in order", and the index turns each into an index scan instead of a sort.

Add a column recipe

  1. Write the migration — backend/migrations/00002_add_labels.sql, e.g. ALTER TABLE cards ADD COLUMN labels TEXT NOT NULL DEFAULT '';
  2. Mirror it in sql/schema.sql so sqlc sees it.
  3. Regenerate — make generate (first time: make install-sqlc). Commit the generated files; they are part of the source.
  4. Add a query to sql/queries.sql if you need to read or write it.
  5. Expose it — DTO field, service mapping, validation, request body.
  6. Update the contract — docs/API.md, then the TypeScript types and normaliser.
  7. Render it — a component, plus the optimistic update in useBoard.updateCard.
  8. Verify — make check and the parity test.

Part 6Frontend design

App Router mental model

Next.js 16 App Router splits code in two. A Server Component (no "use client") runs on the server and is the default. A Client Component ("use client" at the top) runs in the browser. Anything below a client component in the tree is also client code, so the boundary matters: keep data fetching on the server, keep interactivity on the client.

In this app almost everything is a client component, because the whole UI is one long-lived interactive canvas. The two server files that remain are the route shells — they exist so the route structure stays visible in the file tree.

RouteFileWhat happens
/app/(app)/page.tsxStatic shell. A client component fetches the board list and redirects to the first one, or shows "Create your first board".
/board/[boardId]app/(app)/board/[boardId]/page.tsxDynamic. Awaits params, then renders the board screen keyed by the id.

Why the board id is in the URL

Because the active board is part of the address, reload and the browser Back button both work, a user can share a link to a specific board, and a refresh is a normal server-rendered navigation rather than a client-side guess. The route is marked dynamic (the ƒ in the build output) precisely because of the dynamic segment.

The parenthesised folder (app) is a route group: it adds a layout without adding a URL segment. It exists so the side nav and top bar wrap both routes while the URLs stay / and /board/….

The rule to internalise

Components under components/ never call fetch. They receive data and callbacks as props. Everything that touches the network or mutates state lives in hooks/use-board.ts and providers/. That is what makes each component small enough to understand in one sitting, and it is why the drag layer could be changed without touching a single card component.

State ownership

There are exactly three kinds of state, and putting something in the wrong one is the most common way to introduce a bug.

KindWhere it livesExamplesTest
Server stateuseBoard / BoardsProviderBoard, columns, cardsReload the page; it must come back identical.
URL stateThe address barActive board idReload and press Back.
UI stateuseState in the component that owns the interactionIs the drawer open? Am I renaming? Which column is pending delete?Close and reopen; it must reset.

The rule of thumb: if the user would expect it to survive a refresh, it is server or URL state. If it should vanish on refresh, it is UI state. Nothing here persists UI state to localStorage — the theme is the single exception, and that is a deliberate product decision.

The API client

lib/api.ts is the only file that calls fetch. One exported function per endpoint, all returning typed values.

export class ApiError extends Error {
  readonly status: number;   // 0 = never reached the server
  readonly code: string;     // the "error" slug from the envelope
  readonly path: string;
}

Three behaviours matter here, and all three are contract requirements:

  1. Every non-2xx becomes an ApiError. The body is parsed into { error, message }; if the body is not that shape, a per-status fallback message is used. Nothing is ever silently swallowed.
  2. Network failure is status 0. fetch rejecting means "could not reach the server", which is a different problem from "the server said no" and gets a different message.
  3. Responses are normalised. A null slice becomes [] so .map can never throw, and a card's description/assignee become "" rather than null.
// normaliseBoardDetail — the "null slice" trap the contract warns about
return {
  board: raw.board,
  columns: raw.columns ?? [],          // never null in our components
  cards:   (raw.cards ?? []).map(normaliseCard),
};

useBoard

One hook owns a board. It exposes the state, the loading status, and one function per mutation. The interesting part is the write discipline, described next. 

const { state, status, error, reload,
        renameBoard, createColumn, renameColumn, deleteColumn, moveColumn,
        createCard, updateCard, deleteCard, moveCard,
        previewCardMove, restoreSnapshot, getState } = useBoard(boardId);
  • getState() returns the live state from a ref, so drag handlers resolve their destination against the freshest value even before React has re-rendered.
  • previewCardMove and restoreSnapshot are local-only. They let the drag layer move things around on screen and rewind, with no network traffic at all.
  • Every other function returns a boolean (or the created entity) so the caller can keep a form open on failure.

Part 7Deep dives

Drag and drop

Drag and drop is built on @dnd-kit. It is a declarative library: you describe what is draggable and what is sortable, and it works out the pointer maths. What you have to get right is the identity of things and the timing of the save.

Step 1 — one context, two id namespaces

Cards and columns are both sortable and they share a single DndContext. If their ids could collide, dnd-kit would not be able to tell a card from a column. They therefore live in disjoint namespaces, created in one place: 

// lib/constants.ts
export const cardId       = (id) => `card::${id}`;
export const columnId     = (id) => `column::${id}`;
export const columnZoneId = (id) => `columnzone::${id}`;

Every draggable also carries a data payload, and that is what the drop logic actually reads — ids are for dnd-kit, data is for you: 

useSortable({ id: cardId(card.id),
                data: { type: "card", cardId: card.id, columnId: card.column_id } })

Step 2 — three kinds of droppable

Droppabledata.typeRegistered byRole
A cardcarduseSortable in BoardCardDrop on it → take its slot.
A column's card areacolumnZoneuseDroppable in BoardColumnThe forgiving target. Also the only target in an empty column, which is what makes empty columns valid drop targets.
A column bodycolumnuseSortable in BoardColumnDropping on the lane itself appends to the end.

Step 3 — sensors

useSensor(PointerSensor, { activationConstraint: { distance: 6 } })
useSensor(KeyboardSensor, { coordinateGetter: sortableKeyboardCoordinates })

The pointer sensor's 6-pixel activation distance is what lets a plain click on a card open the editor: no movement, no drag. The keyboard sensor is a genuine freebie — focus the grip, press Space, arrow keys move, Space drops — and it is deliberately not disabled.

Step 4 — the visual model

  • The dragged card is rendered again inside <DragOverlay>, which follows the cursor.
  • The original card deliberately does not receive the sortable transform. It stays in place as a dimmed, ring-highlighted placeholder.
  • Its siblings do receive transforms, animated with the transition that useSortable returns. That is where the "cards glide into the new slot" feeling comes from — nothing is animated by hand.

Step 5 — the sequence for a cross-column drag

The bug this shape avoids

If, on drop, you sent "the index of the card I hovered", you would be off by one whenever a preview had already run. Example: previews placed the dragged card at index 0 and the user released over the card now at index 1; sending 1 would jump it to the end. The fix is a single boolean — previewedRef — that says "the local state already holds the answer". 

if (previewedRef.current) {
  toColumnId = currentColumnId;                      // previews already moved it
  toIndex    = index of the card in that column;     // so trust the state
} else {
  toColumnId = over.columnId;                        // no cross-column move yet
  toIndex    = index of the hovered card;
}

Column dragging is deliberately different

Columns get no onDragOver preview. The sortable transform already shows the column sliding into its new slot, and previewing as well makes it jump. On drop, the destination is simply the index of whichever column is under the pointer — which is exactly what dnd-kit's own arrayMove would produce, so the animation and the result agree.

Cancelling is handled explicitly: dropping on nothing, or pressing Escape, restores the drag-start snapshot. The server was never told about the previews, so restoring is the correct and consistent outcome.

Optimistic updates

Optimistic means: change the screen, then tell the server. The user sees the result instantly; the network happens in the background. The three rules are always the same.

  1. Apply locally first. The screen must never wait for a round trip.
  2. Snapshot before mutating. That snapshot is the rollback target.
  3. On failure, restore the snapshot and tell the user. Never fail silently — a card that quietly did not move is worse than an error.

Guarding against out-of-order responses

This is the part people forget. A user can drag a card, then drag it again before the first request returns. If the first response arrives last and is applied, the card jumps back to the old place — a "ghost rewind" the user never asked for.

The fix is a write counter per entity:

const writeSeq = useRef(new Map<string, number>());

function beginWrite(key) {                       // key = "card:<uuid>"
  const next = (writeSeq.current.get(key) ?? 0) + 1;
  writeSeq.current.set(key, next);
  return next;                                   // the ticket number
}
const isLatestWrite = (key, ticket) => writeSeq.current.get(key) === ticket;
const ticket = beginWrite(key);
commit(moveCardInState(before, id, toColumnId, toIndex));   // 1. apply
try {
  const saved = await api.moveCard(id, { column_id, position });
  if (!isLatestWrite(key, ticket)) return;                 // 2. superseded
  commit(reconcileCard(stateRef.current, saved));
} catch (cause) {
  if (!isLatestWrite(key, ticket)) return;                 // 3. do not roll back
  commit(snapshot);                                        //    over a newer write
  toast.error("Could not move the card", describeError(cause));
}

Read the two if guards carefully. A superseded response must neither apply its result nor restore an old snapshot, because either would clobber the newer, still-in-flight edit. The second guard is the one that is easy to leave out.

Why creates are not optimistic

Creating a card or a column needs a server-assigned UUID. A temporary client-generated id would have to be replaced the moment the response arrives, and anything in between — a drag, a delete, a second drag — would be operating on a card that does not exist on the server. Instead the composers show a pending state ("Adding…") and insert the real entity when it arrives. Every update, move and delete is optimistic, because none of them needs a new id.

Theming

Light and dark are two separate colour ramps, not one ramp inverted, so both themes look intentional. The three surface levels are distinct in both: page background, column lane, card.

The Tailwind v4 trap

By default Tailwind v4 compiles every dark: utility into a media query:

/* what v4 does by default */
@media (prefers-color-scheme: dark) { .dark\:bg-black { … } }

That ignores the class we toggle on <html>, so the switch would appear to do nothing and the app would follow the operating system. One line in globals.css redefines the variant as a class strategy: 

@custom-variant dark (&:where(.dark, .dark *));

If you ever delete this line, the toggle silently breaks. It is the first thing to check when someone reports "dark mode stopped working".

The no-flash script

Even with a class strategy, React hydrates after the first paint. Without help, a dark-mode user gets a white flash on every load. The fix is a tiny blocking script in <head> that runs before anything is painted: 

(function () {
  try {
    var k = "kanban.theme";
    var s = null;
    try { s = window.localStorage.getItem(k); } catch (e) {}
    var t = (s === "light" || s === "dark")
      ? s                                                   // the user's choice wins
      : (window.matchMedia("(prefers-color-scheme: dark)").matches
          ? "dark" : "light");                              // otherwise the OS
    var r = document.documentElement;
    r.classList.toggle("dark", t === "dark");
    r.style.colorScheme = t;
  } catch (e) {}
})();

The same resolution is repeated in resolveInitialTheme() inside the provider, because once React takes over it has to know what the script decided. Keep the two in step. colorScheme is set alongside the class so native widgets — the date picker's calendar icon, scrollbars — follow the theme too.

Token model

:root  { --background, --surface, --surface-muted, --surface-strong,
        --border, --border-strong, --muted-foreground,
        --accent, --accent-soft, --danger, --warning, --success, --ring }
.dark  { /* the same names, dark values */ }

@theme inline {                       /* exposes each as a Tailwind colour */
  --color-background: var(--background);
  --color-surface: var(--surface);
  …
}

That is what makes bg-surface, text-muted-foreground and border-border work. To retheme the product, edit the two blocks — never a component.

Dates

The single most common bug in date handling

In JavaScript, new Date("2026-10-15") is UTC midnight, not local midnight. In New York (UTC−4) that is 8pm on the 14th, so any naive toLocaleDateString() displays the 14th. A due date the user typed as the 15th silently becomes the 14th. 

// WRONG — shifts the day for anyone west of UTC
const d = new Date("2026-10-15");
d.toLocaleDateString();     // "Oct 14" in New York

// RIGHT — build a local Date from the parts
const [, m, day] = /^(\d{4})-(\d{2})-(\d{2})/.exec(value);
const d = new Date(2026, 9 - 1, 15);   // local midnight
d.toLocaleDateString();     // "Oct 15" everywhere

lib/dates.ts does exactly that, and additionally rejects overflow like 2026-02-31 (which JavaScript would silently roll into March). The value is never sent to toISOString() anywhere, in either direction.

The backend has the mirror-image rule: Postgres hands back a DATE as UTC midnight, so the API formats it with .UTC().Format("2006-01-02") — the stored day comes out unchanged for every timezone. The two halves agree by construction.

Why due dates also render only after hydration

"Overdue" depends on the user's local today. The server may be in Singapore and the browser in Berlin, so the server-rendered HTML and the first client render could legitimately disagree — React would report a hydration mismatch. The chip therefore formats after mount, keeping the same box size to avoid a visible jump.

Accessibility

  • No colour-only meaning. Priority carries an icon and a word as well as a colour; an overdue date says "Overdue" and swaps the calendar icon for a warning triangle.
  • Every icon-only button has a label. The shared IconButton requires an aria-label as a prop, so you cannot forget one.
  • One focus treatment. A shared FOCUS_RING class is applied to every control, so focus is always visible and always the same.
  • Dragging works without a mouse. dnd-kit's keyboard sensor is enabled and the grip is a real focusable control with its own label.
  • No nested interactive elements. A card body is a plain button; the drag grip is a sibling. Screen readers therefore expose both.
  • Dialogs trap focus, label themselves and restore focus on close (Radix does this); the drawer is a labelled Dialog.Title / Dialog.Description pair.
  • Toasts announce themselves — errors with role="alert", everything else in a polite live region.
  • Nothing is lost by accident. A dirty card drawer intercepts backdrop clicks and Escape and asks before discarding.

Part 8Testing

There are three test layers, and they are not interchangeable. Knowing which one would catch your bug is most of the skill.

Go unit tests

backend/internal/api/service_test.go — pure functions, no database, no HTTP. Run with make test (or cd backend && go test ./...).

Smoke test

backend/test/smoke.ps1 exercises every endpoint against a running server. Run it with make smoke (or ./backend/test/smoke.ps1). It is safe to re-run: it cleans up the scratch board it created even after an interrupted run, and it asserts that positions stay a gap-free 0..n-1 after every move.

Cross-layer parity

The test that matters most for drag and drop

frontend/test/parity.mts imports the real board-state.ts helpers — the same functions the drag layer uses — and runs them against a live API. It then compares what the UI would render with what the server actually settled on, for both a cross-column move and a within-column move. 

cd frontend
npm run parity                                  # uses :8081 by default
KANBAN_API=http://localhost:8080/api/v1 npm run parity

Run it whenever you touch moveCardInState, the drop-target logic, or anything in the Go service that computes an order. "The card lands one slot off after a cross-column drag" is invisible to tests on either side in isolation — only the two halves running against each other will catch it.

What is not covered

Be honest about the gaps so you know where to be careful:

  • No frontend unit tests. The React components are not covered; the pure logic in lib/ is what the parity test exercises.
  • No browser end-to-end tests. Nothing verifies the actual drag gesture, only the index it produces.
  • No load or concurrency testing. The pool is sized for a single user.
  • No auth. There are no users; assignee is free text. Do not build anything that assumes otherwise without a contract change.

Part 10Recipes

Add a field to a card, end to end

Say you want a labels text field. Eight files, in this order:

  1. backend/migrations/00002_add_labels.sql — ALTER TABLE cards ADD COLUMN labels TEXT NOT NULL DEFAULT '';
  2. backend/sql/schema.sql — the same line, so sqlc sees it.
  3. make generate — commit the regenerated store files.
  4. backend/sql/queries.sql — add the column to the create/update/select statements you need.
  5. backend/internal/api/dto.go — add the field to Card and to CardRequest.
  6. backend/internal/api/mapping.go — copy it in cardDTO and normalise it in validateCardFields.
  7. docs/API.md — then frontend/src/lib/types.ts and normaliseCard in lib/api.ts.
  8. Frontend — a control in card-drawer.tsx, a line in CardFace, and the field in the optimistic draft inside useBoard.updateCard.

Then verify: make check, make smoke, cd frontend && npm run parity.

Add an endpoint

  1. Document it in docs/API.md first — path, body, success shape, every error it can return.
  2. SQL — add a named query in queries.sql, regenerate.
  3. Service method in service.go, returning DTOs, raising invalid() / notFound().
  4. Handler in handlers.go: context, decode, call, writeJSON. Nothing else.
  5. Route in router.go with the method prefix.
  6. Unit tests in service_test.go for every validation branch.
  7. Smoke case in test/smoke.ps1.
  8. Client function in frontend/src/lib/api.ts plus its TypeScript type.
  9. Hook method in use-board.ts with the optimistic/rollback pattern.
  10. UI — a component that calls it, and a toast on failure.

Five rules to remember

  1. Ordering is a gap-free 0..n-1 list, renumbered on every move, in one transaction. Never invent a fractional position.
  2. A due date is a calendar day, not an instant. Parse the parts; never new Date(str).
  3. Update the screen first, then the server — and always have a snapshot to roll back to.
  4. Change docs/API.md before you change code, and change both halves together.
  5. Never edit a generated file. Regenerate it.
