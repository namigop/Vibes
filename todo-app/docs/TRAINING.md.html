Maintaining the TODO App

A ground-up tour of this codebase for a junior engineer who is about to own it: how it is put together, why it is put together that way, and exactly where to change things.

1. Start here

Welcome aboard. This document assumes you can read Go and TypeScript but may be new to sqlc, Chi, goose, or containerised development. If any of those are new, this guide explains them where they appear.

The 60-second version

A Next.js page calls a Go REST API. The Go API talks to PostgreSQL through generated code — you write SQL, a tool writes Go. Everything runs in Docker Compose with hot reload. There is no auth and one user.

Your first 30 minutes

  1. Get the stack running

    Follow §13 Running the stack. Expect the first build to take a few minutes while Docker pulls base images.

  2. Click around the UI

    Open http://localhost:3000. Create a todo, tick it, edit it, delete it. Watch the backend logs while you do — every action logs one structured line.

  3. Make a harmless change

    Edit the heading in frontend/app/page.tsx and save. Confirm the browser updates without a manual refresh. This proves hot reload works on your machine before you depend on it.

  4. Run the tests once

    make test. This boots a throwaway Postgres in Docker. Seeing it pass gives you a safety net before you change anything.

2. What this app is

A single-user, unauthenticated CRUD app over one entity: a todo. It was scoped deliberately small so the full stack — build, migrations, codegen, tests, hot reload — could be exercised end to end without feature work getting in the way.

The data model

One table, six columns, defined in backend/migrations/00001_create_todos.sql:

ColumnTypeNotes
idUUIDPrimary key, defaults to gen_random_uuid() via the pgcrypto extension.
titleTEXT NOT NULLRequired, max 200 chars (enforced in Go, not the DB).
descriptionTEXT NOT NULL DEFAULT ''Optional, max 2000 chars. Empty string, never NULL.
doneBOOLEAN NOT NULL DEFAULT FALSEThe completion flag.
created_atTIMESTAMPTZ NOT NULLDatabase clock, not application clock.
updated_atTIMESTAMPTZ NOT NULLBumped on every update via NOW() in the SQL, not Go.
Design decision: no nullable columns

Every column is NOT NULL. This is why the API never has to decide what a missing description means. When you add a field, resist the urge to make it nullable — prefer a sensible DEFAULT.

Explicitly out of scope

Do not assume any of these exist; they were consciously excluded. Adding one is fine, but it is a design change, not a bug fix:

  • Authentication, users, sessions
  • Categories, priorities, due dates, subtasks, recurring tasks
  • Pagination beyond "return everything"
  • Real-time updates (no WebSocket/SSE)
  • Production Dockerfile, CI/CD, deployment config

3. Technology choices

Each choice below was picked deliberately. The "why" column is the part that matters — it tells you when a choice is still right and when it has become a liability.

  • Utility classes; no separate stylesheet to keep in sync, and dark mode is dark: variants on the same element.
    • LayerChosenWhy this and not the obvious alternative
    RouterChi Thin wrapper over net/http. You can read Chi's middleware and drop down to stdlib at any time. Gin/Echo hide the stdlib behind a custom context type, which makes the underlying behaviour harder to look up.
    SQL accesssqlc + pgx/v5 You write real SQL; a generator emits typed Go. Compared with an ORM you keep full control of the query and see exactly what runs. Compared with hand-written pgx code you avoid the scanning boilerplate.
    Migrationsgoose Plain .sql files with -- +goose Up/Down blocks. The library is embedded and run at startup, so there is no separate migration service to keep alive.
    Validationgo-playground/validator Struct-tag rules (validate:"required,max=200") keep the rule next to the field it describes. The frontend validates too, but only for fast feedback — the backend is the authority.
    Logginglog/slog (stdlib) Structured JSON logs with zero dependencies. slog is now stdlib, so there is no reason to pull in zap or zerolog.
    Hot reloadair The de facto Go hot-reload tool. Pinned in the Dockerfile for a reason — see §15.
    FrontendNext.js 14 App Router Chosen over Vite+SPA because it gives room to grow into server rendering. The trade-off: more machinery than a todo app strictly needs.
    Server stateTanStack Query Handles caching, refetching and invalidation so components never hand-roll useEffect + useState + fetch again.
    StylingTailwind CSS
    Config: environment variables, no config library

    backend/internal/config/config.go reads os.Getenv with defaults matching .env.example. Adding a dependency here (Viper, koanf) is not worth it at this size.

    5. Anatomy of a request

    Trace a single POST /api/v1/todos from click to database. Knowing this path is the single most useful thing you can learn about this codebase — most bugs live in one of these stages.

    1. NewTodoForm (onSubmit)
   └─ api.createTodo({title, description})                    lib/api.ts
      └─ fetch POST ${BASE_URL}/todos                          lib/api.ts
         BASE_URL = process.env.NEXT_PUBLIC_API_BASE_URL

2. CORS preflight (browser does this first for POST + JSON)
   └─ OPTIONS /api/v1/todos  →  Access-Control-Allow-Origin: http://localhost:3000

3. chi middleware chain                    httpapi/router.go
   RequestID → RealIP → RequestLogger → Recoverer → CORS

4. TodosHandler.Create                    httpapi/todos_handler.go
   ├─ DecodeJSON  → 400 invalid_body on bad/extra JSON
   ├─ Validate    → 400 validation_failed (title required, max 200)
   ├─ svc.Create  → service layer
   └─ WriteJSON(201, todo)

5. Service.Create                          internal/todo/service.go
   └─ store.CreateTodo(CreateTodoParams)    ← GENERATED, knows the SQL

6. pgx/v5 executes INSERT ... RETURNING     (inside store/queries.sql.go)

7. Row scanned into store.Todo, returned up the stack

8. WriteJSON encodes it → 201 Created
   {"id":"...","title":"...","done":false,"created_at":"2026-...Z"}

9. TanStack Query: onMutated() → invalidate ['todos'] → refetch

10. TodoList re-renders with the new item
    Note step 9

    Mutations do not patch local state. They invalidate the ['todos'] query key, which triggers a refetch. This is deliberately simple and always correct; if you later add optimistic updates, be careful — the backend is the source of truth and can reject a write with 400.

    6. The four backend layers

    The backend is four thin layers. Each one has exactly one job, and each depends only on the layer beneath it. This is what keeps the code testable without a database.

    ┌──────────────────────────────────────────────────────────────┐
│ httpapi  (transport)                                          │
│   parses HTTP, decodes JSON, validates, maps errors to codes   │
│   knows: request/response, status codes, error envelope        │
│   does NOT know: SQL, or what "not found" means in the domain  │
├──────────────────────────────────────────────────────────────┤
│ todo  (domain)                                                │
│   Service: business rules, error translation (ErrNotFound)     │
│   model.go: request/response structs + validation tags         │
│   Store interface: what the domain needs, not what SQL provides │
├──────────────────────────────────────────────────────────────┤
│ store  (persistence — GENERATED)                              │
│   typed methods per query in sql/queries.sql                  │
│   knows: SQL, connection, scanning                             │
├──────────────────────────────────────────────────────────────┤
│ PostgreSQL                                                     │
└──────────────────────────────────────────────────────────────┘

config sits beside these: read once at startup, passed down explicitly.
Nothing reaches for a global.

    Why the Store interface exists

    The domain layer defines the interface it needs, and the generated code happens to satisfy it. This is dependency inversion: the important direction is that todo knows nothing about pgx.

    // internal/todo/service.go
type Store interface {
    ListTodos(ctx context.Context) ([]store.Todo, error)
    GetTodo(ctx context.Context, id uuid.UUID) (store.Todo, error)
    CreateTodo(ctx context.Context, arg store.CreateTodoParams) (store.Todo, error)
    UpdateTodo(ctx context.Context, arg store.UpdateTodoParams) (store.Todo, error)
    DeleteTodo(ctx context.Context, id uuid.UUID) (int64, error)
}

// *store.Queries satisfies this automatically — no adapter, no glue code.
// Tests can pass a hand-written fake instead.
    Gotcha when you change a query

    If you change a query's signature in sql/queries.sql, the Store interface stops matching and the compiler will tell you. That is the intended safety net — do not "fix" it by loosening the interface. Update the interface to match reality.

    Error translation

    The service converts storage errors into one domain sentinel, and only the handler knows how to turn that into an HTTP status:

    // service.go — domain meaning
if errors.Is(err, pgx.ErrNoRows) {
    return store.Todo{}, ErrNotFound
}

// todos_handler.go — HTTP meaning
func (h *TodosHandler) handleServiceError(w http.ResponseWriter, err error) {
    if errors.Is(err, todo.ErrNotFound) {
        WriteError(w, http.StatusNotFound, "not_found", "todo not found")
        return
    }
    h.log.Error("todo service error", slog.Any("err", err))
    WriteInternal(w)
}

    This is why the handler never imports pgx. If you add an error type, give it a sentinel in todo and translate it once in the handler.

    7. Frontend architecture

    Server vs client components

    Most of this app is client-rendered on purpose. Files starting with "use client":

    • app/page.tsx — the main list view
    • app/providers.tsx — TanStack Query client
    • components/TodoList.tsx, TodoItem.tsx, NewTodoForm.tsx, ErrorBanner.tsx

    app/layout.tsx stays a server component so it can render the static shell and mount <Providers> around the interactive tree.

    Why not fetch on the server?

    Server Components would work for the initial list, but every mutation would then need a Server Action or a revalidation, and you would lose the client cache that makes toggling feel instant. Because the API is public and CORS is configured, client-side fetching is simpler and honest. Revisit this if you add auth and want SSR for the first paint.

    The API client

    lib/api.ts is the only place that knows about HTTP. It is deliberately thin and has no React dependency, so it is trivially testable and could be reused in a script.

    const BASE_URL =
  process.env.NEXT_PUBLIC_API_BASE_URL ?? "http://localhost:8080/api/v1";

class ApiClientError extends Error {
  readonly status: number;
  readonly code: string;
  readonly details?: ApiError["error"]["details"];
  // carries the backend's machine-readable code + per-field messages
}

async function request<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`${BASE_URL}${path}`, { ...init, headers: { ... } });

  if (res.status === 204) return undefined as T;   // DELETE has no body

  const body = await res.text();
  if (!res.ok) {
    const err = (body as ApiError)?.error;
    throw new ApiClientError(res.status, err?.code ?? "unknown_error",
                             err?.message ?? `request failed with status ${res.status}`,
                             err?.details);
  }
  return body as T;
}

export const api = {
  listTodos, createTodo, updateTodo, deleteTodo
};
    The frontend does not duplicate validation

    NewTodoForm validates with react-hook-form purely for instant feedback. The backend still validates and still returns 400. If they ever disagree, the backend wins — fix the backend rule and mirror it in the form.

const [client] = useState(() => new QueryClient({
  defaultOptions: {
    queries: { staleTime: 30_000, refetchOnWindowFocus: false, retry: 1 },

    8. Data layer & sqlc

    This is the part that surprises newcomers most, so read it twice.

    You never write the query code

    The workflow is always the same three steps:

    1. Write SQL in backend/sql/queries.sql

      -- name: ListTodos :many
SELECT id, title, description, done, created_at, updated_at
FROM todos
ORDER BY created_at DESC;

-- name: GetTodo :one
SELECT id, title, description, done, created_at, updated_at
FROM todos
WHERE id = $1;

-- name: CreateTodo :one
INSERT INTO todos (title, description)
VALUES ($1, $2)
RETURNING id, title, description, done, created_at, updated_at;

-- name: UpdateTodo :one
UPDATE todos
SET
    title       = COALESCE(sqlc.narg('title'),       title),
    description = COALESCE(sqlc.narg('description'), description),
    done        = COALESCE(sqlc.narg('done'),        done),
    updated_at  = NOW()
WHERE id = sqlc.arg('id')
RETURNING id, title, description, done, created_at, updated_at;

-- name: DeleteTodo :execrows
DELETE FROM todos
WHERE id = $1;

    2. Regenerate

      make generate

      This writes to backend/internal/store/. Those files are GENERATED — never edit them; your changes vanish on the next run.

    3. Call the new method from the service

      Then update the Store interface if the signature changed.

    The annotation vocabulary

    AnnotationReturnsUse when
    :onesingle rowRead or write-one. Errors with pgx.ErrNoRows when nothing matched — this is how you get a 404.
    :many[]RowList queries. See the nil-slice warning below.
    :execerror onlyAlmost never what you want — see below.
    :execrows(int64, error)DELETE/UPDATE where you need to know whether a row actually existed.
    Why :exec cannot express "not found"

    A :exec DELETE never returns pgx.ErrNoRows. Deleting a row that doesn't exist just reports success. Any errors.Is(err, pgx.ErrNoRows) check downstream is dead code, and your API returns 204 for a missing id instead of 404. Use :execrows and branch on affected == 0.

    Nil slices serialise to null

    A :many query returning zero rows gives a nil slice, which Go's JSON encoder writes as null, not []. The frontend then does items.length and throws a TypeError. The service normalises it:

    if items == nil {
    items = []store.Todo{}
}

    Keep this in mind for every new :many query.

    Type overrides — and why they exist

    By default sqlc maps Postgres types to pgx's wrapper structs, which is wrong for this codebase. backend/sqlc.yaml overrides them:

    gen:
  go:
    sql_package: "pgx/v5"
    emit_json_tags: true
    emit_pointers_for_null_types: true
    overrides:
      - db_type: "uuid"
        go_type: { import: "github.com/google/uuid", package: "uuid", type: "UUID" }
      - db_type: "timestamptz"
        go_type: { import: "time", type: "Time" }   # no `package` key here

    This is not cosmetic. Without it, store.Todo.ID is pgtype.UUID, which serialises as:

    {"id":{"Bytes":"b7d4...","Valid":true},"created_at":{"Time":"...","Valid":true}}

    The frontend expects {"id":"b7d4...","created_at":"2026-...Z"} and would render garbage. The package key is also required for the uuid import but must be omitted for time — setting it produces a duplicate time "time" import and the build fails with "time redeclared in this block".

    Why sqlc.narg in the update query

    PATCH is a partial update: omitted fields must be left alone. A plain $1 would overwrite them. sqlc.narg() makes a parameter nullable, and COALESCE(narg, existing_column) means "keep the old value when not supplied". The generated UpdateTodoParams uses *string / *bool, which is why UpdateRequest in model.go uses pointers — nil means "don't change".

    9. Errors & validation

    One error shape, everywhere

    Every non-2xx response uses the same envelope, defined in internal/httpapi/errors.go:

    {
  "error": {
    "code": "validation_failed",
    "message": "request body is invalid",
    "details": [ { "field": "title", "message": "is required" } ]
  }
}
    CodeHTTPMeaning
    validation_failed400A field rule was violated. details is populated.
    invalid_body400Malformed JSON, or an unknown field (the decoder uses DisallowUnknownFields).
    invalid_id400Path id is not a valid UUID.
    not_found404No row with that id.
    internal_error500Anything unexpected. The detail is logged, never returned.

    details is always an array, never null — the error helper coerces it. The frontend's ApiError type in lib/types.ts mirrors this exactly.

    Validation rules

    Rules live as struct tags in internal/todo/model.go, right next to the fields:

    type CreateRequest struct {
    Title       string `json:"title" validate:"required,max=200"`
    Description string `json:"description" validate:"omitempty,max=2000"`
}

type UpdateRequest struct {
    Title       *string `json:"title,omitempty" validate:"omitempty,max=200"`
    Description *string `json:"description,omitempty" validate:"omitempty,max=2000"`
    Done        *bool   `json:"done,omitempty"`
}

    Note omitempty on the update fields: for a pointer, "empty" means nil, so an absent field skips validation. Without it, a PATCH that omits the title would fail as "title is required" — which would make partial updates impossible.

    Turning library errors into friendly text

    Raw validator messages ("field validation failed") are useless to end users. internal/todo/validate.go maps each tag to a human sentence:

    func friendlyMessage(fe validator.FieldError) string {
    switch fe.Tag() {
    case "required": return "is required"
    case "max":     return fmt.Sprintf("must be at most %s characters", fe.Param())
    case "min":     return fmt.Sprintf("must be at least %s characters", fe.Param())
    default:        return "is invalid"
    }
}

    When you add a validation tag, add a case here too — otherwise users see "is invalid" with no explanation.

    10. CORS

    Because the browser loads the app from :3000 and calls the API on :8080, that is a cross-origin request. The backend opts in explicitly in internal/httpapi/middleware.go:

    func CORS(allowedOrigins []string) func(http.Handler) http.Handler {
    if len(allowedOrigins) == 0 {
        allowedOrigins = []string{"http://localhost:3000"}
    }
    return cors.Handler(cors.Options{
        AllowedOrigins:   allowedOrigins,
        AllowedMethods:   []string{"GET", "POST", "PATCH", "DELETE", "OPTIONS"},
        AllowedHeaders:   []string{"Accept", "Authorization", "Content-Type", "X-Request-ID"},
        ExposedHeaders:   []string{"X-Request-ID"},
        AllowCredentials: false,
        MaxAge:           300,
    })
}
    Wildcard origins are a security decision, not a shortcut

    With no auth there is nothing to steal yet. The moment you add cookies or Authorization headers, AllowedOrigins: ["*"] becomes a real vulnerability. Keep the explicit allowlist.

    When the browser blocks you

    Symptoms: the UI loads but every action fails, and the console shows a CORS error. The origin must match exactly including port and scheme. Check:

    1. CORS_ALLOWED_ORIGINS in .env matches the browser URL
    2. It's a comma-separated list, whitespace-trimmed — see splitCSV in config.go
    3. You changed the frontend port? Update this too, then restart the backend

    11. Migrations

    goose applies pending migrations at every backend start (runMigrations in cmd/server/main.go), so there is no separate migration step in normal use.

    -- +goose Up
CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE TABLE todos (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title       TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    done        BOOLEAN NOT NULL DEFAULT FALSE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX todos_created_at_idx ON todos (created_at DESC);

-- +goose Down
DROP TABLE IF EXISTS todos;

    Adding a migration

    1. Create backend/migrations/00002_your_change.sql

      Numbering is sequential. Always write a Down section — it is your rollback.

    2. Mirror the final schema into backend/sql/schema.sql

      This is not optional. sqlc reads schema.sql, not the migrations, to understand your tables. Forget this and sqlc reports unknown columns or generates the wrong types.

    3. Restart the backend and regenerate

      docker compose restart backend
make generate
    Never edit an applied migration

    goose records which version ran. Editing an old file means existing databases never receive your change, and the codebase and the schema silently diverge. Always add a new numbered file.

    Manual control, when you need it:

    make migrate-up       # apply pending
make migrate-down     # roll back one step

    13. Running the stack

    First run

    The make generate step is not optional. sqlc output lives in internal/store/ and is not checked in, so the backend cannot compile until it runs.

    # macOS / Linux / WSL / Git Bash
cp .env.example .env
docker compose build
docker compose up -d postgres
make generate
docker compose up -d

# Windows PowerShell (no make or cp by default)
Copy-Item .env.example .env
docker compose build
docker compose up -d postgres
docker compose run --rm backend sh -c "go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest && sqlc generate"
docker compose up -d

    Then open http://localhost:3000.

    Make targets

    TargetDoes
    make upBuild and start everything in the background
    make downStop and remove containers (keeps data)
    make cleandown -v — also deletes the pgdata volume
    make logsTail all container logs
    make testRun integration tests inside the backend container
    make generateInstall sqlc in the container and run codegen
    make sqlcRun sqlc generate using a host install
    make migrate-up / migrate-downApply / roll back migrations

    Hot reload

    Both services reload on save. The backend runs under air, which watches backend/ and reruns go build -o ./tmp/server ./cmd/server on change. The frontend is the Next.js dev server.

    air uses filesystem polling, and that is deliberate

    .air.toml sets poll = true. With the default poll = false, air relies on inotify, which does not cross Docker Desktop's bind-mount on Windows or macOS. The symptom is nasty: no error, just no reload — you edit code and keep testing the old binary. If you ever see that, check this setting first.

    One related quirk: internal/store is in air's exclude_dir, so regenerating sqlc output will not trigger a rebuild. Touch a watched file, or restart the backend.

    14. Tests

    There is one test file, backend/tests/integration_test.go, and it is an integration test — not a unit test. It boots a real Postgres 16 container with testcontainers-go, runs the real migrations, builds the real router, and drives it with httptest.

    // setup(): the heart of the suite
1. Start a Postgres 16 container (testcontainers)
2. Open it via database/sql + pgx stdlib driver
3. Run goose migrations against it
4. Build the pgxpool the app uses in production
5. Construct store → service → validator → router
6. Return (http.Handler, cleanup)

router, cleanup := setup(t)
defer cleanup()

    Because it uses the real router, the tests cover routing, middleware, validation, the service layer and SQL in one pass — a bug in any of those surfaces as a test failure.

    What is covered

    • Happy path: create → list → get → patch (toggle) → delete → list (empty)
    • Validation: empty title → 400
    • Not found: unknown id → 404

    What is not covered

    • Frontend behaviour — there are no component or E2E tests
    • CORS preflight specifics
    • Partial-PATCH field preservation (i.e. patching only title must not clear done) — worth adding
    • Delete-twice → the second call must 404
    Adding a test is the fastest way to learn this codebase

    Copy the shape of the happy-path test. The whole stack is already wired in setup(), so a new assertion is a few lines. If a bug ever escapes, add the missing assertion here before fixing it.

    docker compose run --rm backend go test ./...     # or: make test

    15. Troubleshooting

    Backend container is up but /healthz fails

    docker compose logs backend

    A compile error means air never started the binary. Read the first error, fix it, and the binary starts automatically.

    Image build fails on COPY go.mod go.sum ./

    go.sum doesn't exist on a fresh clone because it is generated, not committed. The Dockerfile deliberately copies only go.mod; go.sum arrives later via COPY . .. Don't "fix" this by committing an empty go.sum.

    sqlc generate fails to parse the config

    sqlc validates every config key strictly and refuses to start on an unknown one. Read the line number in the error — it points at the offending key. Known valid Go options: emit_json_tags, emit_pointers_for_null_types, sql_package, overrides (nested under gen.go).

    Generated code has pgtype.UUID instead of uuid.UUID

    The overrides aren't matching. They must sit under gen.go.overrides (not at the top level) and use the bare type names uuid / timestamptz.

    Build fails with "time redeclared in this block"

    You set package: "time" on the timestamptz override. Omit the package key — the import path's last segment is already the package name.

    Edits are not showing up in the API

    Check air's poll setting (§13), then confirm the file isn't inside internal/store (excluded from watching). Restart the backend as a blunt fix.

    CORS error in the browser console

    CORS_ALLOWED_ORIGINS must match the browser origin exactly, scheme and port included. Restart the backend after changing it — config is read once at startup.

    Port already allocated

    # in .env
BACKEND_PORT=8081
POSTGRES_PORT=5433
# then: docker compose down && docker compose up -d

    If you move the backend port, also update NEXT_PUBLIC_API_BASE_URL.

    Start completely fresh

    docker compose down -v    # removes containers AND the pgdata volume

    16. Bugs already hit (and their lessons)

    This app shipped with four real bugs. They are worth knowing because each one is a trap that catches people regularly in this stack.

    1. sqlc generated pgx types, breaking the API contract

    bug The service passed uuid.UUID; sqlc generated methods expecting pgtype.UUID. The backend did not compile. Worse, had it compiled without the override, the API would have returned {"id":{"Bytes":"...","Valid":true}} — valid JSON, wrong shape, and a crash only in the browser.

    Lesson: verify the actual JSON body, not just that it compiles. Curl GET /api/v1/todos and read the bytes.

    2. DELETE returned 204 for a missing todo

    bug DeleteTodo was :exec, so the pgx.ErrNoRows branch was unreachable and deleting a nonexistent id returned 204. Clients could not distinguish "deleted" from "never existed".

    Lesson: choose the sqlc annotation that carries the information you need — :execrows for existence checks.

    3. Empty list serialised as null

    bug A :many query with no rows returns a nil slice, which Go writes as null. The frontend does items.length and throws. Fixed by normalising to []store.Todo{} in the service.

    Lesson: Go's nil slice is null in JSON, never [].

    4. Hot reload silently did nothing

    bug air with poll = false never sees host file changes through a Docker Desktop bind mount. No error, no rebuild — you debug code that isn't running. Fixed with poll = true.

    Lesson: when "my change did nothing", verify the running binary is the code you just wrote before investigating the code itself.

    17. Common change recipes

    Add a field to todos (e.g. priority)

    1. Migration add

      -- backend/migrations/00002_add_priority.sql
-- +goose Up
ALTER TABLE todos ADD COLUMN priority TEXT NOT NULL DEFAULT 'medium';
-- +goose Down
ALTER TABLE todos DROP COLUMN priority;

    2. Mirror into sql/schema.sql

      Add the same column to the CREATE TABLE todos block. Required — sqlc reads this file, not the migrations.

    3. Regenerate and wire the types

      docker compose restart backend
make generate

      store.Todo now has Priority. The compiler will point at every place that needs updating — that list is your change list.

    4. Add to the Go request structs

      // internal/todo/model.go
type CreateRequest struct {
    Title    string `json:"title" validate:"required,max=200"`
    Priority string `json:"priority" validate:"omitempty,oneof=low medium high"`
}

    5. Include it in the SQL

      -- name: CreateTodo :one
INSERT INTO todos (title, description, priority)
VALUES ($1, $2, $3)
RETURNING id, title, description, done, priority, created_at, updated_at;

    6. Map it in the service

      func (s *Service) Create(ctx context.Context, req CreateRequest) (store.Todo, error) {
    p := req.Priority
    if p == "" { p = "medium" }
    return s.store.CreateTodo(ctx, store.CreateTodoParams{
        Title: req.Title, Description: req.Description, Priority: p,
    })
}

    7. Update the frontend type and UI

      lib/types.ts, then the components. api.ts needs a new field in createTodo.

    8. Add a test and verify the wire format

      curl -X POST http://localhost:8080/api/v1/todos \
  -H 'Content-Type: application/json' \
  -d '{"title":"x","priority":"high"}'
    Two rules that save time

    1. Never edit internal/store/ — it is regenerated. If a query is missing, add it to sql/queries.sql.
    2. Never forget sql/schema.sql. It is the step everyone skips, and the resulting sqlc error is confusing.

    Add a new endpoint

    1. Add a named query to sql/queries.sql
    2. make generate
    3. Add the method to the Store interface in service.go
    4. Add a service method that translates errors to ErrNotFound
    5. Add a handler in todos_handler.go using DecodeJSON / WriteError
    6. Register the route in router.go (also add the method to the CORS AllowedMethods list if it's not a standard verb)
    7. Add a wrapper to lib/api.ts and a test

    Add a second resource (e.g. projects)

    Follow the same vertical slice, but create a new domain package internal/project/ with its own Service and Store interface, and its own internal/store generated package. Add its routes under r.Route("/api/v1", ...) in router.go. Do not put projects in internal/todo — the boundary is what keeps each package small.

    Add pagination

    Change ListTodos to accept sqlc.arg('limit') and sqlc.arg('offset'), read them in the handler, and return an envelope like {"items":[...], "total":N, "limit":L, "offset":O}. Keep returning [] not null on page 0, and update the Todo list type on the frontend accordingly.

    18. Where to grow it

    Each of these is a real feature, not a small fix. Listed roughly by how much it reshapes the architecture.

    Low effort, high value

    • Frontend tests — Vitest + React Testing Library for the components, or Playwright for a true click-through. Currently the UI has zero automated coverage.
    • Backend unit tests — a fake Store makes internal/todo testable with no containers at all. Fast, and the Store interface already makes this easy.
    • More integration assertions — partial-PATCH preservation, delete-twice, CORS preflight. All cheap given setup() already builds the full stack.
    • A .env.local story — so each developer can override ports without touching the shared file.

    Medium effort

    • Production Dockerfile — multi-stage build, non-root user, static binary. Note the Go image must be bumped in step with any tool that needs a newer Go.
    • CI — go vet, gofmt, sqlc drift detection (regenerate and git diff --exit-code), npm run build. sqlc drift is the one worth having early: it catches someone editing a query without regenerating.
    • Optimistic updates — tick a checkbox and update the cache before the round trip. Requires a rollback path on failure.
    • Health/readiness split — /healthz (process is up) vs /readyz (DB reachable), so an orchestrator does not route traffic to a backend that cannot reach Postgres.

    Larger redesigns

    • Authentication — a users table, a user_id on todos, session or JWT middleware, and scoping every query by owner. The Store interface is the seam: the queries change, the service barely does. Every todos query gains WHERE user_id = ?.
    • Multi-tenancy / sharing — a join table, and the query layer starts returning rows the caller may not see. Authorisation stops being implicit and needs to be deliberate in the service layer.
    • Real-time — SSE or WebSocket so multiple browsers stay in sync. TanStack Query already exposes subscription hooks; the backend needs a change-notification path (Postgres LISTEN/NOTIFY is the cheap version).
    • SSR — move the initial list fetch into a Server Component. The client cache and the CORS arrangement would both simplify, at the cost of a more complex data flow. Only worth it if the first paint matters.
    Adding auth changes the threat model

    Before that work lands: review the CORS allowlist (§10), stop returning detail in 500s (already the case), and make sure DecodeJSON's DisallowUnknownFields stays on. None of this matters much for a single-user app and all of it matters the day it is multi-user.

    19. Pre-merge checklist

    Work through this before asking for review. It catches the failure modes this codebase is actually prone to.

    1. Did you update sql/schema.sql with any migration?

      If you added a migration and forgot this, sqlc generates wrong or fails confusingly.

    2. Did you run make generate and commit the result?

      internal/store/ is generated but is committed so the tree builds without a toolchain. If your change added a query, the generated file must be updated too.

    3. Did you hand-edit anything in internal/store/?

      It is overwritten on every make generate. Move the logic into queries.sql.

    4. Does a new :many query normalise its nil slice?

      Otherwise the API returns null and the frontend crashes on .length.

    5. Does a new DELETE/UPDATE need a 404?

      Use :execrows and check the affected count. :exec cannot express it.

    6. Did you add a validation rule with a friendly message?

      A new tag in validate: needs a matching case in friendlyMessage, or users see "is invalid".

    7. Did you update lib/types.ts alongside the Go model?

      These two are maintained by hand and must match. There is no generated contract.

    8. Have you curl'd the endpoint and read the raw JSON?

      Status codes are not enough — verify field names and value shapes. This is how bug #1 got shipped.

    9. Do make test and the frontend build pass?

      make test
cd frontend && npm run build

    When you find a bug worth remembering, add it to §16 with the lesson, not just the symptom. This app has already produced four non-obvious ones, and the next person will hit at least one of the same traps.
